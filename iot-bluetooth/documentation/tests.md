# 测试策略

## 自动化证据

| 范围 | 命令 | Build 26 结果 |
| --- | --- | --- |
| 生产会话与协议模型 | Python 测试调用 `swiftc` 编译生产 `BLEControlSession`、协议和模型，再运行 Swift Harness | 通过，覆盖两种认证回调顺序、同连接连续动作、大端解析和协议参考载荷 |
| iOS 源码守卫 | `PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s tests -v` | 14 项通过，确认 Build 26、常连接、回执、回读、界面边界和危险命令无生产入口 |
| iOS 无签名编译 | `xcodebuild -project IoTBluetooth.xcodeproj -scheme IoTBluetooth -destination 'generic/platform=iOS' CODE_SIGNING_ALLOWED=NO build` | 通过，`BUILD SUCCEEDED` |
| iOS 模拟器界面 | iPhone 17 Pro、iOS 26.5 模拟器构建、启动、三页主界面和设备密钥页视觉与辅助功能树检查 | 通过，无截断和重复长按控件，禁用状态可朗读，未连接真实 BLE 设备 |
| iOS 签名与安装 | 签名 `xcodebuild`、`codesign --verify`、`devicectl device install app` 和设备端应用读回 | 通过，设备端读回 `1.0 (26)`，未启动 App |

源码守卫固定以下边界：

- Xcode Target 不包含远程管理器、远程页面和 BLE 事件队列。
- 协议模型只包含 V1.2.5 文档的 11 条 BLE 命令，不引入归档扩展命令。
- 生产管理器只主动发送认证、主锁、状态、车辆信息和旧数据命令。
- `0x61`、`0x62` 和 `0x81` 没有界面或主动发送入口。
- 同一认证连接允许连续操作，但同一时刻只允许一个协议操作。
- 主锁必要回执后回读主锁和车辆状态，协议结果一致时保持连接。
- 写操作的未知结果会断开，App 不自动重连或重试。
- 旧数据清除必须先读取并由用户确认。
- 活跃 App 不包含 LocalAuthentication、Face ID 权限或设备所有者验证调用。
- 旧骑行用户 ID 不进入脱敏诊断。
- 界面不显示“开锁成功”或“关锁成功”。
- Build 26 的统一视觉组件已进入 Xcode Target，长按按钮包含进度、减少动态效果和辅助功能状态说明。

## 2026 年 8 月 23 日实车证据

- 用户在 Build 24 的同一 BLE 连接内连续完成主锁开锁和关锁，中途没有断开，仪表、动力和轮毂锁物理状态正确。
- Mac CoreBluetooth 探针使用当前生产协议代码完成认证，并在同一连接内连续两轮读取 `0x31` 和 `0x60`，两轮结果一致且连接稳定。
- `0x51` 真实旧骑行数据读取和解析通过。经用户明确授权，`0x52` 永久清除成功，`0x31` 回读确认旧数据标志已经清除。
- `0x61` 在锁车和开锁通电状态下都返回成功，但 `0x60` 回读模式没有变化，因此不能判定生效。
- `0x62` 在锁车状态下发送非持久化关闭巡航，15 秒内无回包，未自动重试。
- 电池锁、车轮锁和钢缆锁三项 `0x81` 查询分别无回包。因为没有明确前置锁态，未发送任何外部锁解锁或上锁命令。
- 设置验收序列结束时曾出现逻辑已关锁、轮毂锁已锁、仪表仍亮。单次重复关锁无回包，随后执行不含设置的干净开锁和关锁复位循环。用户最终确认仪表熄灭、车辆动力断开、轮毂锁锁住，过程中状态恢复正常。

## 自动化不能证明

- iPhone 是否能发现并持续连接真实车辆 IoT。
- 仪表、动力和轮毂锁是否达到正确物理状态。
- 设备成功码是否代表控制器或机械部件实际生效。
- 连续操作后仪表是否稳定，不出现重启或供电残留。

本车仪表与车辆动力绑定。仪表亮表示有动力，仪表灭表示无动力。主关锁验收必须同时观察仪表熄灭和轮毂锁锁住，不能只看 App 或协议回包。
