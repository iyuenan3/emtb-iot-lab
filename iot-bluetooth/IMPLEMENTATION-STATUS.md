# 功能实现状态

当前代码基线为 Build 25。产品保持纯蓝牙和常连接，只开放已经在本车上取得可靠实车证据的功能。Build 24 用于完成协议验收，Build 25 根据验收结果移除了不可靠入口。

## 当前开放功能

| 范围 | 状态与证据 |
| --- | --- |
| BLE 连接 | 手动扫描精确目标、发现 NUS 服务、使用 8 字节设备密钥认证 |
| 常连接会话 | 一个物理连接只认证一次，连续操作复用连接 Key，不自动重连或重试 |
| 主锁 | `0x05` 开锁、`0x15` 关锁、必要回执、`0x31` 回读和幂等保护，用户已完成同连接连续实车验收 |
| 车辆状态 | `0x31` 主锁、电压、固件和旧数据标志，`0x60` 电量、模式、速度和里程，真实设备同连接连续两轮读取稳定 |
| 旧骑行数据 | `0x51` 读取成功，`0x52` 经用户授权永久清除成功，`0x31` 回读确认标志已清除 |
| 本机安全 | 设备密钥保存在 iOS Keychain，连接 Key 只存在于当前连接内存，Face ID 和网络代码不进入目标 |
| 失败策略 | 写操作超时、写入失败、回读不一致或提前断连均标记未知并断开，不重连、不重试 |

当前 App 的主动发送范围为：

`0x01`、`0x05`、`0x15`、`0x31`、`0x51`、`0x52`、`0x60`。

`0x10` 只作为设备协议错误回包处理，不是主动功能入口。

## 已停用功能

| 命令 | 实车结果 | Build 25 处理 |
| --- | --- | --- |
| `0x61` | 锁车和开锁通电状态下均返回成功，但 `0x60` 回读模式没有变化 | 移除设置界面和发送入口 |
| `0x62` | 锁车状态下发送非持久化关闭巡航，15 秒内无回包 | 移除设置界面和发送入口 |
| `0x81` | 电池锁、车轮锁、钢缆锁三项查询分别发送，均无回包 | 移除查询和控制入口，未发送任何外部锁写操作 |

`0x61` 通电验收后，主关锁虽然返回成功且 `0x31` 为已关锁，现场却出现仪表仍亮、轮毂锁已锁的异常组合。单次重复关锁没有回包，随后执行一次不含设置的干净开锁和关锁复位循环，最终用户确认仪表熄灭、车辆动力断开、轮毂锁锁住，状态恢复正常。不能证明异常一定由 `0x61` 引起，但它已经超过继续开放设置功能的安全阈值。

本车的仪表与车辆动力绑定：仪表亮表示车辆有动力，仪表灭表示车辆无动力。任何协议锁态都不能代替这项现场判断。轮毂锁只随已验证的主锁流程联动，不使用 `0x81` 独立控制。

## 仍保留的协议参考

`OmniProtocol.swift` 和 `Models.swift` 仍保留 V1.2.5 文档中 `0x61`、`0x62`、`0x81` 的编号、载荷模型和解析工具，用于说明协议来源与保留自动测试。生产管理器和界面没有这些命令的主动发送入口。

归档代码中的 `0x85`、`0x91`、`0xFA`、`0xFB`、`0xFC`、`0xFF` 等扩展命令从未纳入当前 App。
